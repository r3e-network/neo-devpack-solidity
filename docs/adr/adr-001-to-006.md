## ADR-001: Hexagonal Architecture for Compiler Core

**Status**: Proposed  
**Date**: 2026-07-04

### Context

The current architecture has 11 top-level modules with unclear boundaries. The CLI module (151 files) contains 6 distinct responsibilities: compilation orchestration, bytecode assembly, manifest generation, IR optimization, standard JSON processing, and integration tests. Developers can't easily determine where compilation logic lives versus test infrastructure versus optimization.

The runtime module (167 files) has bidirectional coupling between 4 subsystems (bridge ↔ execution ↔ state ↔ storage), making changes ripple unpredictably.

### Decision

Adopt a hexagonal architecture for the compiler core with bounded contexts:

- **Parser** (frontend + solidity) — source → contract metadata
- **IR** — contract metadata → intermediate representation
- **Codegen** (extracted from CLI) — IR → NeoVM bytecode
- **Optimizer** (extracted from CLI) — IR optimization passes
- **Manifest** (extracted from CLI + neo) — bytecode → NEF + manifest
- **Runtime** (separate) — NeoVM execution simulator

Plus a **Shared Kernel** containing only immutable primitives (opcodes, types, spec tables).

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Hexagonal (chosen)** | Clear boundaries, one-way flow, testable contexts | More modules to navigate initially |
| Layered | Simpler mental model | Doesn't address god-module problem; layers can be thick |
| Microservices | Strong isolation | Overkill for a compiler; no network boundary needed |
| Status quo | No migration effort | Debt compounds; velocity decreases |

### Consequences

- **Easier**: Understanding where to make changes, testing individual contexts, onboarding
- **Harder**: More modules to navigate initially, slightly more boilerplate for context boundaries
- **Trade-off**: More structure upfront in exchange for long-term maintainability

## ADR-002: Runtime as Separate Bounded Context with Port Interface

**Status**: Proposed  
**Date**: 2026-07-04

### Context

The runtime module (167 files, 17K LOC) is test-only infrastructure compiled by default. It has bidirectional coupling between 4 subsystems. The compiler core doesn't need the runtime for production builds — only tests and fuzzing do.

The current `runtime` feature flag partially addresses this, but the coupling remains even when compiled out. The bridge ↔ execution dependency is especially problematic: bridge delegates to execution, but execution calls back to bridge for EVM compatibility.

### Decision

Make the runtime a separate bounded context communicating through a `RuntimePort` trait:

```rust
pub trait RuntimePort: Send + Sync {
    fn execute(&mut self, bytecode: &[u8], context: &ExecContext) -> ExecResult;
    fn get_storage(&self, key: &[u8]) -> Option<Vec<u8>>;
    fn set_storage(&mut self, key: &[u8], value: &[u8]);
}
```

The compiler core defines the port; the runtime implements it. The runtime is gated behind the `runtime` feature flag (already partially implemented). The 4 internal subsystems are decoupled via their own trait interfaces.

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Port/adapter (chosen)** | Clean separation, runtime compiled out, testable independently | One indirection level; port trait maintenance |
| Direct calls with feature flag | No indirection | Current approach; coupling remains when compiled out |
| Separate crate | Strongest isolation | Workspace overhead; defer to Phase 5 |
| Delete the runtime | Simplest | Too risky; 965 tests depend on it |

### Consequences

- **Easier**: Production builds without runtime overhead, testing in isolation, evolving runtime independently
- **Harder**: One level of indirection for runtime calls, port trait must be maintained
- **Trade-off**: Slight runtime overhead (trait dispatch) in exchange for compile-time isolation

## ADR-003: Trait-Based Extension Points

**Status**: Proposed  
**Date**: 2026-07-04

### Context

Adding new Solidity version support requires changes across `frontend` (parser version gate), `solidity` (analysis rules), `ir` (lowering), and `devpack` (Solidity libraries). There's no mechanism to isolate version-specific behavior.

Similarly, adding a new NeoVM native contract requires changes in 4 places: runtime handler, Solidity wrapper, hash constant, and spec table. The recent v0.28.1 audit found 20 missing runtime handlers and 14 missing Solidity wrappers — exactly the kind of gaps that a plugin system would prevent.

### Decision

Introduce three trait-based extension points:

**SolidityVersion**:
```rust
pub trait SolidityVersion: Send + Sync {
    fn version_string(&self) -> &str;
    fn supported_features(&self) -> SolidityFeatures;
    fn validate_pragma(&self, pragma: &str) -> Result<(), PragmaError>;
    fn parse_rules(&self) -> &ParseRules;
}
```

**NativeContractHandler**:
```rust
pub trait NativeContractHandler: Send + Sync {
    fn contract_hash(&self) -> &str;
    fn handle_method(&self, method: &str, args: &[StackItem]) -> Result<StackItem, RuntimeError>;
    fn supported_methods(&self) -> &[&str];
}
```

**OptimizerPass**:
```rust
pub trait OptimizerPass: Send + Sync {
    fn name(&self) -> &str;
    fn min_level(&self) -> u8;
    fn run(&self, module: &mut ir::Module) -> Vec<OptimizationWarning>;
}
```

Each extension is a trait implementation registered in a registry. The compiler dispatches to the registered implementation.

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Traits + registry (chosen)** | Compile-time safety, runtime flexibility, idiomatic Rust | Indirection for dispatch |
| Plugin DLLs | Maximum flexibility | Overkill for a compiler; no dynamic loading needed |
| Feature flags | Already used | Doesn't scale to 11+ native contracts |
| Hard-coded dispatch | Zero overhead | Current approach; doesn't scale; gaps go unnoticed |

### Consequences

- **Easier**: Adding new versions/contracts/passes touches only the implementation + registration
- **Harder**: One level of indirection for dispatch, trait definitions must be maintained
- **Trade-off**: Slight dispatch overhead in exchange for extensibility and gap prevention

## ADR-004: Strangler Fig Migration Strategy

**Status**: Proposed  
**Date**: 2026-07-04

### Context

The system has 965 passing tests and ~87% famous-contract compilation coverage. A big-bang rewrite would risk losing this coverage and introducing subtle semantic regressions. The team is small (1-2 developers).

The v0.28.1 audit showed that even small changes (fixing type strictness, adding missing handlers) can surface subtle issues. A full rewrite would multiply this risk by orders of magnitude.

### Decision

Use the strangler fig pattern — new architecture grows alongside the old, gradually replacing it across 5 phases:

1. **Phase 1** (v0.29.x): CLI decomposition — extract codegen, optimizer, manifest
2. **Phase 2** (v0.30.x): Runtime isolation — decouple 4 subsystems via port interface
3. **Phase 3** (v0.31.x): Extension points — trait plugins for versions, contracts, passes
4. **Phase 4** (v0.32.x): File refactoring — break 13 files >800 lines
5. **Phase 5** (v1.0, optional): Crate split — workspace with separate crates

Each phase ships independently with zero test regressions. The public API (`compile_contracts`, `disassemble_neovm_bytecode`) stays stable throughout.

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Strangler fig (chosen)** | Preserves tests, incremental, low risk, continuous delivery | Longer migration; temporary pattern coexistence |
| Big-bang rewrite | Faster to target shape | High regression risk; loses test coverage; blocks other work |
| Branch and merge | Doesn't block main | Long-lived branch diverges; merge hell at the end |
| Status quo | No effort | Debt compounds; velocity decreases |

### Consequences

- **Easier**: Safe migration, continuous delivery, no "big bang" risk
- **Harder**: Temporary coexistence of old and new patterns, some duplication during migration
- **Trade-off**: Longer migration time in exchange for zero-downtime refactoring

### Phase Dependencies

```
Phase 1 (CLI decomp) ──→ Phase 2 (Runtime isolation)
                    └──→ Phase 3 (Extension points)  [parallel with Phase 2]
                                              ──→ Phase 4 (File refactoring)
                                                              ──→ Phase 5 (Crate split, optional)
```

Phases 1 and 3 can run in parallel (different files, no conflicts). Phase 2 depends on Phase 1 (runtime port needs the codegen context to exist). Phase 4 depends on Phases 2+3 (file splitting benefits from the new structure). Phase 5 is optional.

## ADR-005: Shared Kernel Immutability Rule

**Status**: Proposed  
**Date**: 2026-07-04

### Context

The shared kernel (opcodes, types, spec tables, storage keys) is referenced by all contexts. If the kernel contains business logic or mutable state, every context becomes coupled to that logic. Changes to kernel logic ripple across the entire system.

Currently, `src/runtime/spec/` contains lookup tables that are shared between the disassembler and the runtime. This is correct — they're immutable data. But there's no explicit rule preventing business logic from creeping into shared modules.

### Decision

The shared kernel contains only immutable primitives:

| Component | Content |
|-----------|---------|
| `opcode` | NeoVM opcode enum + constructors (pure functions) |
| `type_system` | Type definitions (no logic) |
| `spec` | Opcode/syscall/native lookup tables (static data) |
| `storage_key` | Key format utilities (pure functions) |
| `utils` | Pure utility functions |

**Rules**:
1. No I/O (no file reads, no network calls, no printing)
2. No state mutation (all functions are pure)
3. No business logic (no compilation decisions, no semantic analysis)
4. Depends on nothing (no external crate dependencies beyond std + serde)
5. Any context may depend on the kernel; the kernel depends on no context

### Consequences

- **Easier**: Any context can depend on the kernel without coupling concerns
- **Harder**: Some utility functions that could live in the kernel must live in individual contexts instead (minor duplication risk)
- **Trade-off**: Minor code duplication risk in exchange for clean dependency graph

## ADR-006: Directory Depth Limit (≤4 levels)

**Status**: Proposed  
**Date**: 2026-07-04

### Context

The current runtime module has directory nesting up to 7+ levels:

```
src/runtime/execution/execution_impl_part2_native/contract_management.rs
```

This depth causes:
- Long import paths that are brittle and hard to refactor
- IDE navigation difficulties
- `#[path = "..."]` anti-pattern temptation (which was previously cleaned up)
- Naming conventions like `execution_impl_part2_native` that encode implementation history rather than domain meaning

### Decision

Enforce a maximum directory depth of 4 levels from `src/`:

```
src/runtime/vm_core/native/contract_management.rs   (4 levels — OK)
src/runtime/execution/execution_impl_part2_native/contract_management.rs  (5 levels — too deep)
```

The `execution_impl_part2_native` naming convention is replaced with domain-based naming (`native/`).

### Consequences

- **Easier**: Shorter import paths, better IDE navigation, clearer domain meaning
- **Harder**: Some modules may need to be merged or reorganized to fit the limit
- **Trade-off**: Occasional wider directories in exchange for shallower depth
