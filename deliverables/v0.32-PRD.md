### 当前基线（仓库核实）

- 编译器已具备 Solidity 0.5.x–0.8.x 输入能力（0.8.x 为主要支持线），输出 `.nef` 与 `.manifest.json`；支持标准 JSON、优化、NEP 标准检测和 Neo-Express 烟测。
- `src/` 仍存在 6 个生产 Rust 文件超过 800 行（另有测试大文件）；`tooling/packages/` 存在 5 个超过 800 行的 TypeScript 文件；`devpack/contracts/` 有 2 个大型 Solidity 聚合封装文件。仓库架构文档将 v0.32 定义为“大文件拆分”阶段，但实际文件清单应以 CI 扫描为准。
- `neo-forge init/test/clean` 可用，`neo-forge build` 当前已具备 Standard JSON 编译、产物收集和增量缓存实现；`watch`、依赖管理及部分 cast/anvil/coverage/fork 能力仍为未实现或忽略并给出提示的范围。
- 嵌入式运行时覆盖核心 opcode、存储/迭代器/运行时/密码学 syscall，但异常栈展开和复杂操作 gas 仍需按 Neo N3 规范核验；迭代器流式化、ByteString/Buffer 区分、完整原生合约方法和实时链访问器仍是已记录限制。
- `Neo.Sol.Runtime` 是独立实验性 C# EVM 模拟库，不属于 `neo-solc` 编译链，v0.32 不得将其与编译器运行时混为一体。

## 2. 产品定义

### 2.1 产品目标

1. **降低维护风险**：以领域边界拆分编译器、工具链和 DevPack 中的超大生产模块，保持单一职责，使后续 feature/fix 可以局部修改和审查。
2. **保持编译产物与行为稳定**：重构必须保持公共 CLI/API、NEF/Manifest 结构、字节码语义和现有测试结果；任何行为变化必须有明确诊断或版本说明。
3. **提高端到端可用性与可验证性**：让 `neo-solc`、`neo-forge build`、DevPack 合约和嵌入式运行时拥有一致的回归、兼容性和限制说明，便于开发者安全迁移与发布。

### 2.2 用户故事

- As a **Solidity 合约开发者**, I want to run `neo-forge build` on a project using the documented Solidity range so that I can obtain valid `.nef` and `.manifest.json` artifacts without manually invoking `neo-solc`.
- As a **编译器贡献者**, I want parser/IR/codegen/manifest and optimizer responsibilities to be separated into focused modules so that I can add a feature without editing an unrelated monolithic dispatcher.
- As a **DevPack/标准库使用者**, I want generated manifests, native-call wrappers, and NEP-11/17/24 mappings to remain compatible so that existing contracts do not require source changes after v0.32.
- As a **QA/安全审计人员**, I want deterministic conformance, fuzz, integration, and smoke gates so that a refactor cannot silently change bytecode, diagnostics, storage semantics, or runtime behavior.
- As a **工具链维护者**, I want unsupported commands/options to fail with stable, actionable diagnostics rather than appear implemented so that users understand the supported surface.

## 4. 范围界定

### 4.1 本版本包含

- Rust 编译器内部模块化：frontend/solidity/IR/optimizer/codegen/manifest/CLI 之间保持单向依赖和稳定边界。
- TypeScript `tooling/packages` 中与编译、artifact、配置和错误处理直接相关的模块化与跨包回归。
- DevPack Solidity wrapper/standard 合约的接口兼容审查、生成产物和标准检测回归。
- 嵌入式 runtime 的 P1 正确性核验、gas/限制文档及测试门禁。
- `neo-forge build` 的稳定构建体验、Standard JSON 契约、缓存和错误诊断。

### 4.2 本版本明确不包含

- 不重写 Solidity 编译器前端，不承诺完整 EVM/assembly/Create2 语义；Neo 特有映射仍以支持矩阵为准。
- 不把独立实验性 C# `Neo.Sol.Runtime` 合并进 `neo-solc`，不发布其 NuGet 产品或承诺与编译器产物存储布局互通。
- 不承诺 P2 的流式迭代器、完整 native contract/live-chain state、真实 `neo-cast send/deploy`、完整 `neo-anvil`、watch/依赖管理/coverage/fork。
- 不修改源码作为本 PRD 交付的一部分；实现需由工程任务另行落地并通过门禁。

## 5. UI/交互草案（CLI 体验）

- `neo-forge build [--profile <name>] [--force] [--quiet]`：显示 profile、源文件数、产物路径、缓存命中；成功返回 0，失败返回非零。
- 错误输出统一为 `CODE: message`，尽可能附 `file:line:column`、severity 和修复建议；JSON/CI 场景提供机器可解析字段。
- 未实现选项必须输出“未支持 + 替代命令/后续计划”，不得输出成功假象。
- `--quiet` 仅抑制进度信息，不得吞掉错误详情；构建产物路径遵守 profile 的 `out` 配置。

## 6. 待确认问题（最多 3 条）

1. **v0.32 的拆分门槛是否统一为所有一方生产代码单文件 ≤800 行，还是仅约束 Rust `src/`？** 该决定影响 tooling 与 DevPack 两个聚合文件是否纳入 P0。
2. **P1 runtime parity 是否以 Neo N3 哪个节点/规范版本作为唯一基准（当前文档指向 v3.10.0+）？** 该决定影响 gas 表、异常边界和 conformance 向量。
3. **`neo-forge build` 的配置兼容目标是否仍为独立 `neo-foundry.toml`（兼容 Foundry 风格字段），而非完整 `Foundry.toml`？** 该决定影响配置解析范围与发布承诺。
